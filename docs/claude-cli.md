# Claude по подписке: провайдер `claude-cli`

Провайдер с `type: "claude-cli"` даёт доступ к моделям Claude по подписке Claude Pro/Max,
используя **официальный Claude Code CLI** как транспорт. CLI запускается отдельным процессом
на каждый запрос, получает переписку кадрами `stream-json` и возвращает ответ потоком
`stream-json`, который aiproxy транслирует в обычный Anthropic SSE.

Ключевая идея: aiproxy не изображает из себя клиента Anthropic и не работает с токеном
подписки. Он запускает настоящий клиент и передаёт ему ровно один ход модели.

## Что видит клиент

| Что | Как |
|---|---|
| Эндпоинт | `POST /v1/messages` (нативно), `POST /v1/responses` при `convert_to_responses: true` |
| Формат | Anthropic Messages на входе и выходе; для Responses работает общий обратный конвертер |
| Модель | Нативный ID, например `claude-sonnet-5-5`. Префикс провайдера к нему не добавляется и не срезается |
| Стриминг | Да: `content_block_start` / `text_delta` / `thinking_delta` / `signature_delta` / `tool_use` / `message_delta` / `message_stop` |
| Токены | Из захвата реального ответа Anthropic (`input`, `output`, `cache_read`, `cache_creation`) |
| Заголовки | `X-Request-ID`, `X-Provider`, `X-Upstream-Model` |

## Жизненный цикл одного запроса

```
клиент ──POST /v1/messages──► aiproxy
                               │
                               ├─ 1. buildClaudeRequest: валидация + перевод в кадры
                               ├─ 2. проверка входа CLI (CLAUDE_CONFIG_DIR)
                               ├─ 3. prepareClaudeProc: argv + файлы запроса
                               ├─ 4. admission relay на 127.0.0.1:<random>
                               ├─ 5. spawn claude (свой process group)
                               ├─ 6. replayHistory: история кадрами + ожидание ack
                               ├─ 7. закрыть stdin → CLI делает один запрос к Anthropic
                               │      (через релей, который правит cache_control)
                               ├─ 8. чтение stream-json: дельты → SSE клиенту
                               └─ 9. финал: usage/stop_reason из захвата релея
```

Всё, что относится к запросу, живёт в собственном временном каталоге (`system.md`,
`settings.json`, `tools.json`) и удаляется при закрытии.

### 1. Перевод запроса в кадры

`buildClaudeRequest` (`providers/claudecode.go`) собирает:

- **system prompt** — поле `system` верхнего уровня ставится перед текстом из сообщений
  `role: system|developer`, склейка детерминирована (разделитель — пустая строка). Лимит 4 МиБ;
  этот текст уходит в `--system-prompt-file`.
- **история** — сообщения превращаются в кадры `user` / `assistant`; соседние пользовательские
  кадры склеиваются; `tool_result` сохраняет `tool_use_id` и `is_error`.
- **reasoning** — блоки `thinking` переносятся только вместе с `signature`; `redacted_thinking`
  и неизвестные типы блоков отбрасываются (нативный парсер их не примет).
- **картинки** — только `base64`; ссылка на удалённый URL не скачивается (иначе прокси тянул бы
  произвольный сетевой контент на пути запроса), вместо неё модель получает текстовую пометку.
- **инструменты** — имена нормализуются: `mcp__hermes__<wire>`, где `<wire>` — имя клиента или
  его усечённая форма с хэшем (`wireName`), потому что CLI ограничивает имя 64 символами.
  Обратное отображение `wire → host` ведётся на запрос.
- **extra body** — `tools`, `thinking` (включая `display`), `output_config.effort`,
  `max_tokens`, `stop_sequences` уезжают в `CLAUDE_CODE_EXTRA_BODY` через приватный
  `settings.json`, а не через переменные окружения: полный инвентарь инструментов не влезает в
  лимит длины одной переменной.

Валидация fail-closed: некорректный запрос не доходит до модели. Отклоняются:

| Ситуация | Причина |
|---|---|
| `tool_choice` не `auto` | `tool_choice` с принудительным выбором не выражается в кадрах |
| история кончается `assistant` или пустым user-сообщением | assistant prefill в stream-json не выражается |
| `role: system` после начала переписки | системные сообщения обязаны идти первыми |
| имя инструмента не из `[A-Za-z0-9_-]` | нативный MCP-протокол такое имя не примет |
| два инструмента дают одинаковое имя после усечения | коллизия сделала бы вызовы неразличимыми |
| system prompt длиннее 4 МиБ, тело запроса длиннее 64 МиБ | защита от неограниченного роста |

### 2–3. Что отключено у CLI

CLI запускается так, чтобы он не мог вести себя как агент:

```
claude -p --model <модель>
  --input-format stream-json --output-format stream-json --verbose --include-partial-messages
  --tools ''                      # встроенные инструменты выключены
  --system-prompt-file <файл>     # промпт клиента, а не однострочный дефолт CLI
  --settings <файл>               # CLAUDE_CODE_EXTRA_BODY
  --setting-sources ''            # пользовательские настройки не читаются
  --strict-mcp-config             # только наш MCP-сервер
  --disable-slash-commands        # никаких слэш-команд
  --max-turns 1                   # один ход
  --permission-mode dontAsk       # нечего подтверждать
  --no-session-persistence        # сессии не сохраняются
  --mcp-config <json>             # инертный инвентарь инструментов
```

Дополнительно в окружении: `CLAUDE_CODE_MAX_RETRIES=0`, `DISABLE_AUTO_COMPACT=1`,
`DISABLE_COMPACT=1`, `ENABLE_TOOL_SEARCH=false`, `CLAUDE_CODE_TOTAL_TOKENS_REMINDER=off`
(напоминание о бюджете меняется от запроса к запросу и ломало бы кэшируемый префикс),
`CLAUDE_CODE_MAX_OUTPUT_TOKENS` из `max_tokens` клиента.

### 4. Admission relay: одно поколение на запрос

CLI умеет сам повторять генерацию даже с `--max-turns 1` и отключёнными HTTP-ретраями. Чтобы
один клиентский запрос не списал подписку дважды, aiproxy поднимает на `127.0.0.1:0`
одноразовый HTTP-релей со случайным путём `/admit/<token>` и передаёт его CLI как
`ANTHROPIC_BASE_URL`:

- первый `POST /v1/messages` пересылается на реальный upstream;
- любой последующий — локальный `429 admission: this request already used its single upstream attempt`;
- служебные пробы CLI (`/v1/models`, health, `count_tokens`) проходят без расхода слота и не
  пишутся в журнал как генерация;
- слот занимается под тем же мьютексом, которым проверяется, поэтому конкурентная проба не
  может его отобрать.

Релей же является точкой учёта: он захватывает ответ целиком (текст, reasoning, аргументы
инструментов, usage, stop_reason) до того, как собственная recovery-логика CLI успеет его
подменить, и передаёт статус первой попытки наверх — поэтому `429`/`529`/`401` от Anthropic
доходят до клиента своим статусом, а не превращаются в `200` с текстом ошибки внутри.

### 5. Рабочий каталог

CLI подставляет свой `cwd` в блок `# Environment` каждого запроса, а этот блок попадает внутрь
кэшируемого префикса. Поэтому все запросы процесса запускаются в одном общем каталоге
`/tmp/claude-cli-cwd-<uid>` (права `0700`, каталог наш, симлинк и чужой каталог отвергаются).
Если подходящего каталога нет, используется пер-запросный — запрос работает, но кэш не
попадает.

### 6. Воспроизведение истории

Исторические кадры отправляются с `shouldQuery: false`; CLI обязан ответить
подтверждением с `num_turns: 0`. Если он ответил иначе, значит поддержка replay-контракта
потеряна, и запрос завершается ошибкой — молча продолжать нельзя, история была бы искажена.
Завершающий кадр уходит без `shouldQuery`, после чего stdin закрывается: CLI отвечает на него
одним поколением.

### 7. Кэш: правка тела перед upstream

CLI ставит message-уровневый `cache_control` на контекст, который сам добавляет к отвеченному
ходу (дата, напоминание про аккаунт), а следующий запрос этот контекст уже не повторяет.
Из-за этого закэшированный префикс не находился и каждый ход оплачивался по цене создания
кэша.

Перед отправкой в Anthropic релей правит тело в два шага, строго в этом порядке:

1. `restoreQueriedTurn` — восстанавливает кадр `tool_result` до того вида, который прислал
   клиент (срезая нативную приписку);
2. `pinMessageBreakpoint` — переносит единственный message-брейкпоинт на контент, который
   следующий запрос воспроизводит байт-в-байт.

Маркеры `tools`/`system` не трогаются, число брейкпоинтов не растёт. Тело, которое не удалось
разобрать или согласовать, уходит как есть: правка может стоить попадания в кэш, но не хода.
Оба состояния (`cli→relay` и `relay→upstream`) пишутся в журнал при включённых телах — иначе
аранжировку самого CLI не увидеть.

### 8–9. Ответ и учёт

- Стрим: `200` коммитится лениво, на первом содержательном событии. Отказ upstream до контента
  сохраняет свой статус; оборванный на `200` ответ отдаётся как `502`.
- Блоки инструментов объявляются только в самом конце: частичный набор вызовов не должен
  попасть к хосту.
- `signature_delta` пробрасывается обязательно — без подписи блок reasoning отбрасывается на
  следующем ходе и многоходовое рассуждение теряется.
- Токены и `stop_reason` берутся из захвата релея, а не из самоотчёта CLI; запись журнала
  получает `upstream_called: true`, токены и заголовки квоты подписки
  (`anthropic-ratelimit-unified-5h-*`, `-7d-*`).

## Креды и изоляция окружения

- Вход выполняет сам CLI: `claude auth login` пишет `.credentials.json` в
  `CLAUDE_CONFIG_DIR` (по умолчанию `<каталог токенов>/claude`, в Docker — том `auth-data/`).
  aiproxy этот файл не читает, не копирует, не обновляет и не передаёт по сети.
- Дочернему процессу передаётся белый список переменных: `PATH`, `TMPDIR`/`TEMP`/`TMP`,
  локаль, `SSL_CERT_FILE`/`SSL_CERT_DIR`, `CLAUDE_CLI_TIMEOUT`. Всё credential-содержащее и всё,
  что влияет на маршрут трафика, отбрасывается.
- `HOME` подменяется пустым каталогом рядом с логином. Иначе CLI нашёл бы `~/.claude`
  машины и молча работал бы под чужим аккаунтом вместо явного `401`.
- `ANTHROPIC_BASE_URL` указывает на релей; `NO_PROXY` всегда содержит loopback, иначе хоп до
  релея ушёл бы в прокси и упал.

## Ошибки

| Ситуация | Что видит клиент |
|---|---|
| Нет входа в CLI | `401` с инструкцией выполнить `docker compose run --rm aiproxy` |
| `rate_limit` от Anthropic | `429` |
| `billing_error` | `402` |
| `authentication_failed` | `401` |
| `overloaded` | `529` |
| `server_error` | `503` |
| Молчание CLI дольше `read_idle_seconds` | `504`, код `native_stream_failed` |
| Ответ пришёл, но неполный (`message_stop` не пришёл) | `502`, код `incomplete_upstream_response` |
| Ошибка уже посреди стрима | терминальное `event: error` с `status` и машинным кодом |
| Нет `claude` в системе | `503` с подсказкой про `npm install -g @anthropic-ai/claude-code` |

Прозаическая формулировка Anthropic не цитируется в теле клиенту: строка вида
`not your usage limit` внутри отрицания читается хостом как вердикт о биллинге и обрывает ход.
Точная цитата остаётся в логе.

## Установка CLI

В Docker-образе CLI уже стоит (закреплённая версия, см. `ARG CLAUDE_CLI_VERSION` в
`Dockerfile`) — версия важна, потому что транспорт опирается на чувствительные к версии
интерфейсы: подтверждение replay, `--include-partial-messages`, `--system-prompt-file`,
`--max-turns`.

При запуске бинаря без Docker:

```bash
npm install -g @anthropic-ai/claude-code
claude auth login          # войти в подписку
export CLAUDE_CLI_PATH=$(command -v claude)   # если бинарь не в PATH сервиса
```

## Почему такая схема корректна

Инженерные факты, на которых она держится:

1. **Работает официальный клиент, а не его имитация.** Запросы к Anthropic отправляет сам
   Claude Code — тот же бинарь, что и при обычной работе. Прокси не подделывает ни
   `User-Agent`, ни заголовки идентичности, ни формат запроса: всё, что видит Anthropic,
   сформировано официальным клиентом.
2. **Авторизация штатная.** Используется обычный вход по подписке, выполняемый самим CLI, и
   его собственный файл кредов. aiproxy не извлекает, не хранит и не переносит токен
   подписки, поэтому нечего подделывать и нечего переиспользовать вне клиента.
3. **Нет обхода лимитов.** Один клиентский запрос — одно поколение: повторные попытки CLI
   отбиваются локально (admission relay). Прокси не ретраит сам и не множит запросы к
   подписке.
4. **Нет агентской самодеятельности.** Инструменты, слэш-команды, настройки пользователя и
   персистентность сессий выключены флагами; инструменты клиента объявлены модели, но любой
   вызов отвечает `Denied`, то есть исполняет их только клиент.

Это описание того, как устроен код. Вопрос «допускает ли мой сценарий использования условия
Anthropic» — вне компетенции программы: условия подписки задаёт Anthropic, и перед
промышленной эксплуатацией их стоит прочитать самостоятельно.

## Что проверить при проблемах

| Симптом | Куда смотреть |
|---|---|
| `401` сразу при старте | есть ли `<каталог токенов>/claude/.credentials.json`; не истёк ли вход |
| Клиент видит «пустой ответ» | журнал: `reason`, `upstream_called`, `status`; лог процесса: `claude-cli request failed` |
| Reasoning не отображается | приходит ли `thinking.display` от клиента и `signature_delta` в ответе |
| Кэш не читается (`cache_read` ~0) | один ли `cwd` у процессов, включены ли тела (`cli→relay`/`relay→upstream`) |
| Долгие паузы в генерации | `read_idle_seconds`: это пауза молчания, длинная генерация не обрывается |
| `429 admission` в логе CLI | это локальный отказ второй попытки, а не лимит Anthropic |
